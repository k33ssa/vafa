# vpn-guard — не пускает в приложение, пока не поднят VPN

Системный демон (LaunchDaemon, работает от root). Пока VPN не обнаружен:

1. **снимает бит `+x`** с исполняемых файлов внутри `.app` — приложение не открывается
   ничем: ни двойным щелчком, ни из Dock, ни из Spotlight, ни через `open -a`,
   ни прямым вызовом бинаря из терминала;
2. **замораживает** (`SIGSTOP`) уже запущенные процессы приложения — или закрывает их,
   если так настроить.

Когда VPN поднимается — права возвращаются, процессы размораживаются с того же места.

---

## Claude: приложение, сайт и CLI без VPN

В конфиге по умолчанию уже стоит всё для этого:

* **Claude.app** в `APPS` — запуск блокируется, открытое окно замерзает
  (все 33 процесса бандла, включая помощников в `Frameworks/` и `Helpers/`);
* **подсети Anthropic** в `BLOCK_NETS` — через `pf` режется сеть к claude.ai,
  claude.com, anthropic.com и api.anthropic.com. Это закрывает сайт **в любом
  браузере** и `claude` в терминале. Уже открытые соединения обрываются;
* **проверка VPN** — `route` и `geo`: маршрут идёт через туннель **и** Cloudflare
  видит выход не из стран блокировки (по умолчанию RU, CN, BY, IR; выбираются в щите,
  хранятся в `/usr/local/etc/vpn-guard.countries`). Если Cloudflare не ответил — считается, что VPN нет
  (лучше заблокировать лишний раз, чем пропустить).

Когда VPN включён, сеть к Anthropic разрешена **только через туннельный интерфейс**.
Поэтому если VPN отвалится, трафик режется сразу, не дожидаясь следующей проверки.

Пока VPN нет, Claude не работает — в том числе и чтобы помочь снять блокировку.
Снимается локально: `sudo vpn-guard unlock`.

## После перезагрузки

Работает само, ничего запускать не нужно:

* демон лежит в `/Library/LaunchDaemons` с `RunAtLoad` — стартует при загрузке,
  ещё до входа в систему; `KeepAlive` перезапускает его, если он упадёт;
* блокировка запуска хранится на диске и переживает перезагрузку;
* правила `pf` при перезагрузке сбрасываются, но демон ставит их заново на первом
  же круге и заново включает `pf`.

На старте сети ещё нет, Cloudflare не отвечает → блокировка **включается**, пока
VPN не поднимется. То есть после перезагрузки Claude откроется только после
подключения VPN.

## Установка

```
sudo ./install.sh
sudo nano /usr/local/etc/vpn-guard.conf     # вписать приложения
```

Конфиг перечитывается на лету, демон перезапускать не нужно.

Проверить:

```
sudo vpn-guard status
```

## Настройка

Всё в `/usr/local/etc/vpn-guard.conf`.

### Что охраняем

```sh
APPS=(
  "/Applications/Telegram.app"
  "/Applications/Google Chrome.app"
)
```

### Как определяется VPN

`VPN_CHECK` — список правил, `VPN_REQUIRE` — `all` (все, по умолчанию) или `any` (любое).

| правило | что проверяет |
|---|---|
| `route` | маршрут по умолчанию идёт через туннель (`utun*`, `ppp*`, `ipsec*`, `tun*`, `tap*`) |
| `nc:Имя` | сервис с таким именем в `scutil --nc list` в статусе `Connected` |
| `scutil` | подключён **любой** VPN-сервис |
| `iface:utun5` | на интерфейсе есть IPv4-адрес |
| `default-iface:utun5` | маршрут по умолчанию именно через этот интерфейс |
| `proc:openvpn` | запущен процесс с таким именем |
| `script:/путь` | свой скрипт, код возврата 0 = VPN есть |

**Осторожно с `scutil`.** На этой машине Tailscale числится `Connected` практически
всегда, поэтому правило `scutil` («любой VPN подключён») будет врать, что VPN есть,
даже когда основной туннель отвалился. Проверено 2026-09-10. Поэтому по умолчанию стоит
связка, которая требует и то и другое:

```sh
VPN_CHECK=( route "nc:Happ Plus" )
VPN_REQUIRE=all
```

Имена сервисов посмотреть: `scutil --nc list`.

**Проверь настройку в обоих состояниях** — включив и выключив VPN:

```
sudo vpn-guard check
```

Должно давать «ПОДНЯТ» при включённом VPN и «ВЫКЛЮЧЕН» при выключенном. Если при
выключенном VPN всё ещё «ПОДНЯТ» — правило подобрано неверно, ужесточи его.

### Что делать при падении VPN

```sh
ON_DOWN=freeze   # заморозить процессы, ничего не теряется (рекомендуется)
ON_DOWN=kill     # закрыть: SIGTERM, затем SIGKILL. Несохранённое может пропасть
LOCK_LAUNCH=1    # снимать +x, чтобы приложение вообще не открывалось
GRACE=0          # сколько секунд терпеть падение VPN до блокировки
MATCH_ANY_PATH=0 # 1 = ловить процессы приложения даже из копии бандла в другом месте
```

## Команды

```
sudo vpn-guard status      # состояние VPN, приложений и демона
sudo vpn-guard check       # только проверка VPN, код возврата 0/1
sudo vpn-guard lock        # заблокировать сейчас, вручную
sudo vpn-guard unlock      # АВАРИЙНО снять все блокировки
sudo vpn-guard uninstall   # выгрузить демон, всё разблокировать
```

Журнал: `/usr/local/var/log/vpn-guard.log`, плюс `log show --predicate 'process == "logger"'`.

## Если что-то пошло не так

Демон **не разблокирует приложения при остановке** — это сделано намеренно, чтобы
блокировку нельзя было снять простым выключением демона. Поэтому если ты снял демон
неправильно (не через `uninstall`), приложения останутся заблокированными.

Разблокировать:

```
sudo vpn-guard unlock
```

Если и скрипт потерялся — руками:

```
sudo chmod +x "/Applications/Имя.app/Contents/MacOS/"*
```

## Чего этот инструмент НЕ делает — читать обязательно

* **Это не защита от тебя самого.** Всё держится на правах root. Любой, у кого есть
  `sudo` (то есть ты), может выгрузить демон и вернуть права одной командой. Инструмент
  спасает от привычки и невнимательности — «открыл мессенджер на автомате, а VPN отвалился»,
  — но не от осознанного обхода.

* **Сетевой блок — только для адресов из `BLOCK_NETS`.** Это не общий killswitch:
  остальной трафик мимо VPN не режется. Заморозка процессов открытые соединения
  тоже не рвёт — поэтому для Claude и добавлен `pf`.

* **Системные приложения Apple заблокировать нельзя.** Safari, Почта и прочее защищены SIP,
  снять с них `+x` не выйдет. Демон напишет об этом в журнал; для таких приложений
  работает только заморозка/закрытие процессов.

* **Копию бандла в другом месте блокировка запуска не покрывает** — снятие `+x` привязано
  к пути. Частично лечится `MATCH_ANY_PATH=1`: тогда процессы ловятся по имени
  исполняемого файла независимо от того, откуда запущены.

* **Обновление приложения возвращает `+x`.** Демон снимет его снова в течение `INTERVAL`
  секунд. Но само обновление во время блокировки может пройти криво — обновляйся с
  поднятым VPN.

* **Окно на старте системы.** Демон стартует не мгновенно. Если на момент выключения
  приложение было разблокировано, в первые секунды после загрузки оно технически
  успеет открыться. На практике демон стартует раньше входа в систему.

* **Claude.app принадлежит тебе, а не root.** Вернуть `+x` можно без sudo, но демон
  снимет его снова через `INTERVAL` секунд. Сетевой блок `pf` без sudo не снять.

## Мини-приложение в строке меню (VPN Guard.app) — 2026-09-28

Значок-щит в строке меню: зелёный — VPN поднят, красный — блокировка, оранжевый — демон
не отвечает. В меню — состояние по каждому приложению (`запуск: …, процессов: N,
заморожено: M`) и «Выбрать приложения…» (галочки по всем .app из /Applications).

* Состояние: демон пишет `/usr/local/var/vpn-guard/status.json` (читается без sudo).
* Выбор: сохраняется в `/usr/local/etc/vpn-guard.apps` (root, 644) через запрос пароля.
  **Если этот файл есть — он главнее `APPS` в конфиге.** Принимаются только .app из
  `/Applications` и `~/Applications`.
* Сборка: `./app/build.sh`, установка вместе с демоном: `sudo ./install.sh`.

### Что исправлено 2026-09-28
* **Ложные блокировки.** 372 из 441 блокировок в журнале были с `страна: ?` —
  Cloudflare не ответил за 4 с при живом туннеле. Теперь 3 попытки (вторая по IP
  1.1.1.1), а при полном молчании на том же интерфейсе ещё `GEO_STALE` (60 с) верим
  последнему ответу. Смена интерфейса или 60 с без ответа — блок, как раньше.
* **Проверка прав конфига** сравнивала с десятичным `22` вместо восьмеричного `022`:
  файл с правами 644 отвергался как «доступный на запись всем».
* Для Claude.app снять `+x` не выходит — это не SIP, а защита macOS «Управление
  приложениями» (бинарь принадлежит aks). Сообщение исправлено и пишется один раз.
  Работает заморозка процессов.
